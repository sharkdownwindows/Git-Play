# GitScope — final report

## Executive summary

GitScope addresses a narrow learning problem: Git beginners see commands and text output, but often cannot see how commits, branch pointers and `HEAD` change. The project provides an interactive terminal, commit-DAG visualization, eight guided levels, automatic goal checking, undo/redo, a five-command reference and a Verification view.

This is a Tier 1-only static web product. Its repository model covers `commit`, `branch`, `switch`, `checkout` and `merge`. It does not cover file content, staging, `git add`, content conflicts, remote operations or progress synchronization. The narrow scope makes the state model deterministic and allows the engine to be compared directly with real Git.

The verification report bundled in this checkout was generated by [GitHub Actions run 36834371216](https://github.com/sharkdownwindows/GitPlay/actions/runs/36834371216) from source commit [`741eba72faed313cf0fc6e2fb4c60e8c35268dfd`](https://github.com/sharkdownwindows/GitPlay/commit/741eba72faed313cf0fc6e2fb4c60e8c35268dfd). It reports 6,160/6,160 differential cases passing the hard gate and no hard divergence. This evidence applies to that SHA, not automatically to later commits.

User evaluation is not complete: the raw CSV contains a header and zero participant rows. Therefore learning gain, task completion, time-on-task and usability findings are all `N/A`, not zero.

## 1. Problem and scope

### Problem

Git's command-line interface exposes history indirectly. New learners must infer three related ideas at once:

1. commits form a directed acyclic graph through parent links;
2. branches are movable names pointing to commits; and
3. `HEAD` is either attached to a branch or detached at a commit.

GitScope makes those state changes visible immediately after each supported command. Guided levels then ask learners to produce a target graph rather than merely repeat command syntax.

### Delivered scope

- A pure TypeScript engine for five Git commands.
- Terminal parsing, command history and Git-style result/error output.
- Deterministic DAG layout and SVG rendering of commits, parents, branches and `HEAD`.
- Eight levels covering first commit, branching, switching, detached `HEAD`, recovery, fast-forward and two-parent merges.
- Automatic goal checking by DAG isomorphism, with branch and `HEAD` placement preserved.
- Undo/redo based on `RepoState` snapshots.
- Browser-local level progress.
- Command Reference and Verification screens.
- Differential testing against Git 2.43 plus layout and browser benchmarks.

### Explicit non-goals

The product does not implement a working tree, staging area, file snapshots, `git add`, content-level merge conflicts, remotes (`clone`, `fetch`, `pull`, `push`), rebase, tags or arbitrary Git options. The four staging-related fields retained in `RepoState` are contract seams and remain `null`; they are not implemented features.

## 2. Architecture

```text
Browser
  Terminal -> parser -> engine -> RepoState -> layout -> SVG graph
                         |  |         |
                         |  |         +-> level checker
                         |  +-> undo/redo snapshots
                         +-> application store -> React screens

  localStorage <-> level progress
  verification.json -> Verification screen

Build/CI
  generated command sequences -> GitScope engine --+
  generated command sequences -> Git 2.43 ---------+-> normalize -> compare
  synthetic DAGs -> layout/browser benchmark ------+-> verification.json
```

The main design decisions are:

- **Pure core:** `src/core/` imports no React, DOM, browser or UI module. The Node harness imports the same engine used by the UI.
- **Separated validation:** `src/terminal/parse.ts` validates syntax. The engine validates repository state and returns `Result`; it does not throw for user errors.
- **Single state contract:** `RepoState` is JSON-serializable and shared by the engine, visualizer, level checker and history.
- **Deterministic layout:** `src/viz/layout.ts` derives positions without mutating `RepoState`. The same state always produces the same layout.
- **Store-owned UI changes:** command execution, level selection and history integration flow through the application store.
- **Local progress only:** the browser stores `LevelRecord` values in `localStorage`.
- **Static verification:** CI writes `public/verification.json`; the frontend validates and renders it but does not manufacture fallback results.

## 3. Five-command engine

| Command | Accepted forms | Modeled behavior |
|---|---|---|
| `commit` | `git commit`; `git commit -m "message"` | Creates `cN` with the current commit as parent. Moves the current branch when attached, or moves detached `HEAD`. |
| `branch` | `git branch`; `git branch <name>` | Lists branches or creates a named pointer at the current commit without switching. Invalid/duplicate names and a repository with no commit are handled as state errors. |
| `switch` | `git switch <branch>`; `git switch -c <branch>`; `git switch --detach <commit-or-branch>` | Attaches to an existing branch, creates and attaches to a branch, or explicitly detaches at a commit/branch tip. A bare commit target is rejected without `--detach`. |
| `checkout` | `git checkout <branch-or-commit>`; `git checkout -b <branch>` | Attaches to a branch, detaches at a commit, or creates and attaches to a branch. |
| `merge` | `git merge <branch>` | Returns already-up-to-date, fast-forwards when possible, or creates a commit with ordered parents `[current, target]`. |

The engine models graph and reference semantics, not file changes. Consequently, non-fast-forward merge can create a two-parent commit but cannot discover a content conflict. IDs, messages and timestamps are deterministic simulator data; IDs are not Git object hashes.

## 4. Verification

### 4.1 Differential testing

The harness executes the same abstract command sequence against GitPlay and a temporary real Git repository. Real Git commits use `--allow-empty`; locale and user configuration are isolated. Since Git hashes cannot be compared directly, both repositories are normalized by creation order, parent structure, branches and attached/detached `HEAD`.

The gate distinguishes:

- **Hard divergence:** repository state, success/failure status or error class differs. This fails CI.
- **Soft divergence:** only human-readable output differs. This is recorded but does not fail CI because Git wording and hashes differ from the simulator.

They are grouped as `branch` 3,979; `checkout` 6,125; `commit` 6,125; `merge` 1,973; and `switch` 1,175. The nightly job also ran the invalid-command `ErrorClass` gate successfully. The schema does not publish its case count, so this report does not invent one.

### 4.2 Benchmark

Layout uses a deterministic synthetic DAG with seed 42, two warm-ups and seven measured iterations per size. The following values come directly from `public/verification.json` for the same CI source SHA:

| Commits | Layout median | Layout p95 |
|---:|---:|---:|
| 100 | 0.231 ms | 0.290 ms |
| 1,000 | 1.350 ms | 1.884 ms |
| 10,000 | 15.136 ms | 23.792 ms |
| 100,000 | 324.989 ms | 346.369 ms |

The least-squares log-log slope of the four published medians is approximately `1.050`. This is consistent with near-linear scaling over the measured range, but it is an empirical fit, not a proof of runtime complexity.

These large synthetic graphs locate implementation limits; normal educational levels are much smaller.
